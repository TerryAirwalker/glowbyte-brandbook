# GlowByte Design — потребительский скилл

**Версия скилла: 1.11**

Публичный, самообслуживаемый скилл. Не требует токена и доступа к приватным
репозиториям — все данные бренда берутся из публичного манифеста.

## Источник данных

```
https://raw.githubusercontent.com/TerryAirwalker/glowbyte-brandbook/main/manifest.json
```

Скачать/прочитать этот `manifest.json` в начале работы. Не собирать материалы по
памяти — все цвета/шрифты/лого/правила брать из манифеста (см. `entrypoint`/`routing`
в самом манифесте — они описывают, какие разделы читать под какую задачу).

### Рапорт о версиях при запуске (обязательно)

Загрузка бренда не должна быть «молчаливой». Сразу после чтения манифеста **выведи
пользователю короткий видимый рапорт** — чтобы он знал, что данные бренда реально
подтянуты из источника (а не собраны по памяти), какая версия брендбука прочитана и
какая версия скилла запущена. Показывать всегда, в том числе когда всё актуально.

1. Из загруженного `manifest.json` возьми `meta.version` — это версия брендбука/манифеста.
2. Версию ЭТОГО скилла возьми из его шапки («Версия скилла: X.Y»).
3. Сверь запущенную версию скилла с ОПУБЛИКОВАННОЙ: скачай (с обходом кэша, `?ts=<эпоха>`)
   `https://raw.githubusercontent.com/TerryAirwalker/glowbyte-brandbook/main/skill/glowbyte-design/SKILL.md`
   и возьми «Версия скилла» из его шапки.
4. Выведи одним компактным блоком:
   - `✓ Брендбук GlowByte подтянут из источника (…/main): manifest vX.Y`
   - если запущенная версия скилла == опубликованной →
     `✓ Скилл glowbyte-design vX.Y — актуальная версия`
   - если опубликованная НОВЕЕ запущенной →
     `⚠ Запущен glowbyte-design vX.Y, в источнике уже vZ.W — перезапусти сессию, чтобы подтянуть свежую версию`
   - если запущенная НОВЕЕ опубликованной (локальная правка ещё не опубликована) —
     тоже отметь это явно (`ℹ …`).

Версии скилла и брендбука НЕ обязаны совпадать (скилл эволюционирует чаще, чем брендовые
токены). «Актуальность» проверяется отдельно: манифест всегда свежий (берётся из `main`),
а версия скилла — сверкой запущенной копии с опубликованным raw.

### Геометрические формы (готовый набор)

Фирменные плоские формы в 4 цветах (orange/green/yellow/blue) — в папке `shapes/`
публичного репозитория ассетов. 10 типов × 4 цвета: `cube-`, `arc-`, `quarter-`,
`circle-dot-`, `rings-`, `rings-quarter-`, `dots-`, `chevron-col-`, `chevron-div-`,
`square-quarter-`. Пример:

```
https://raw.githubusercontent.com/TerryAirwalker/glowbyte-brand-assets/main/shapes/cube-orange.svg
https://raw.githubusercontent.com/TerryAirwalker/glowbyte-brand-assets/main/shapes/arc-blue.svg
https://raw.githubusercontent.com/TerryAirwalker/glowbyte-brand-assets/main/shapes/chevron-div-yellow.svg
```

Правила применения форм — в брендбуке (раздел «Компоненты» → «Правила применения»):
не более 1–2 акцентов на слайд, формы в углах и не поверх текста, рыжий акцент обязателен.

Важно: некоторые файлы в `shapes/` отдаются без атрибута `xmlns` на корневом `<svg>`.
Это валидный XML, но Chromium/Playwright отказывается рендерить такой файл как
растровое изображение через `<img src="...svg">` (падает молча, без сетевой ошибки —
показывает иконку «битой картинки»). Перед использованием любого файла из `shapes/`
как `<img>` — открой его и, если `xmlns="http://www.w3.org/2000/svg"` отсутствует на
корневом `<svg>`, добавь его в локальную копию перед рендерингом.

`Montserrat-var.ttf` — переменный шрифт (ось `wght` 100–900): одним файлом покрывает все
начертания (Light 300 … Bold 700). Используй его для web/HTML/SVG/CSS-материалов
(`@font-face` + `font-weight`). Для `docx/pptx/pdf` встраивай статические
`Montserrat-Regular.ttf` / `Montserrat-Bold.ttf` (Office надёжнее работает с дискретными
файлами весов).

Рыжий логотип — по умолчанию (белый/чёрный фон), белый логотип — для цветного/чёрного
фона (см. `manifest.json` → `colors.forbidden`: рыжий логотип на цветном фоне запрещён).
`glowbyte-mark.svg` — отдельный знак (без слова "lowbyte"), для мест где полный
wordmark не влезает (favicon, мелкий бейдж, аватар); `fill="currentColor"`, перекраска
через CSS `color` — только в пределах фирменной палитры (см. `forbidden`).
Шрифты встраивать в готовые файлы (docx/pptx/pdf), не полагаться на системный Montserrat.

## Презентации: обязательные вопросы о формате и шрифтах (обязательно)

Если задача — **создать или переверстать презентацию** (слайд, дек, `.pptx`/`.pdf`,
многослайдовый материал), то ДО начала сборки обязательно задать пользователю вопрос —
даже если он явно не спрашивал про формат. Один вопрос из двух пунктов:

1. **Формат выдачи** — всегда спрашивать. Варианты: `PPTX`, `PDF`, `PPTX + PDF`,
   опционально `+ PNG` отдельными картинками.
2. **Встраивание шрифтов** — спрашивать **условно**, и только когда выбран
   **редактируемый** формат (`PPTX`/`DOCX`): встраивать ли Montserrat/JetBrains в файл
   (портативно, но тяжелее) или нет (легче, но на чужом ПК без шрифта вид «поедет»).
   Для **невекторно-редактируемых/растровых форматов** — `PDF`, `PNG` — вопрос про
   шрифты **НЕ задавать**: там шрифты всегда «впечатаны» в файл, выбора нет.

Логика короткая: формат — спрашиваем всегда; шрифты — только если формат редактируемый.
Не задавать вопрос про шрифты, если пользователь уже выбрал только PDF/PNG. Если
пользователь сам сразу указал и формат, и (для редактируемого) режим шрифтов —
повторно не переспрашивать.

## Слайды: надзаголовок, рыжий/жёлтый акцент, футер, фирменные фигуры (обязательно)

Правила, выведенные из практики; применять к слайдам всегда, когда уместно.

1. **Надзаголовок — отдельной строкой НАД заголовком.** Если у слайда есть надзаголовок
   (kicker / надпись-рубрика над основным заголовком), он ставится ОТДЕЛЬНОЙ строкой над
   заголовком слайда и выравнивается по левому краю заголовка — НЕ в одну строку с ним.
   Техническая тонкость: если для точного bbox (проверка непересечения с декором) блок
   сделан `inline-block`/`fit-content`, то надзаголовок и заголовок, будучи соседями,
   слипнутся в одну строку. Чтобы этого не было — надзаголовку задать
   `display:block; width:fit-content; align-self:flex-start;` (тогда он и на своей строке,
   и bbox остаётся узким для проверки).

2. **Рыжий обязателен на КАЖДОМ слайде (хотя бы одним элементом).** На каждом слайде
   должен присутствовать минимум один рыжий `#FE6A00` элемент — но это может быть и
   маленький элемент: полоска-разделитель под заголовком, буллет-маркер, номер, уголок
   карточки, значок. Обязателен сам факт присутствия рыжего, а не его площадь. Жёлтый
   НЕ отменяет и НЕ заменяет это требование.

3. **Тёплый акцент-заливка на холодном фоне — жёлтый, а не рыжий.** Это отдельное правило
   от предыдущего. Когда на тёмном/цветном холодном фоне (сине-зелёный градиент) нужен
   крупный/тонкий тёплый акцент — акцент-текст, тонкая обводка карточки, стрелки, метки
   «стало», свечение — используй жёлтый `#FFB000`: рыжий в этих ролях на холодном фоне
   рябит. При этом обязательный рыжий элемент из правила 2 всё равно остаётся на слайде
   (например, полоска-`rule` под заголовком рыжая, а акцент-обводка/стрелки — жёлтые). На
   светлом фоне тёплый акцент-заливка остаётся рыжим `#FE6A00`.

4. **Подпись/логотип в футере — цвет по фону.** «GlowByte» и логотип в нижнем колонтитуле
   выбирают цвет по фону слайда: на цветном/тёмном фоне — белый (`#fff`), на светлом/белом
   фоне — рыжий `#FE6A00`. Рыжая подпись на цветном фоне рябит — не ставить рыжий футер на
   цветных слайдах. Технически: базовый `.footer .brandname{color:#FE6A00}` и переопределение
   `.footer.on-dark .brandname{color:#fff}` (класс `on-dark` вешать на футер цветных слайдов).

5. **Фирменные фигуры — в карточки, а не «в воздух».** Геометрические примитивы
   (кубики, дуги, точки, кольца, четверти) не развешивать произвольно по углам слайда —
   они читаются как случайно висящие. Интегрировать их в контент: как угловой акцент
   карточки (заполненный угол — фигура `quarter-*`, вписанная в угол карточки через
   `overflow:hidden`) или как иконку элемента (`cube-*`, `circle-dot-*` рядом с текстом
   карточки, в цвет карточки). Свободно стоящая крупная геометрия допустима только как
   угловой коллаж на обложке/разделителе, а не на рабочих контентных слайдах.

## Самопроверка перед выдачей

См. `manifest.json` → `self_check_before_delivery.checklist` — пройти обязательно.

## Графика никогда не наслаивается на текст (обязательно)

Декоративные фирменные элементы (кольца, дуги, точки, шевроны, свечения) размещаются
только в углах и по краям, в СВОБОДНЫХ зонах — и никогда не перекрывают текст, логотип
или разделители. Полупрозрачность декора не оправдывает наслоение: текст поверх/под
графикой читается грязно.

Это надо не «прикидывать на глаз», а **проверять численно** перед выдачей:

1. После рендера получи bounding box каждого текстового элемента (заголовок, лид,
   kicker, числа/подписи карточек, теги, футер, логотип) и каждого декоративного
   элемента (Playwright: `element.bounding_box()`).
2. Убедись, что bbox любого декора НЕ пересекается с bbox ни одного текстового
   элемента (пересечение прямоугольников). При пересечении — сдвинь/уменьши декор или
   обрежь его за край холста, и перерендери.
3. Экспортируй финальный PNG только после того, как проверка прошла. Удобно оформить
   это как хард-ассерт в скрипте рендера (при пересечении — не сохранять файл, а падать
   с ошибкой), чтобы битый макет физически не мог уйти пользователю.

Подсказки по зонам: нижняя и верхняя полосы часто заняты футером/шапкой на всю ширину —
там декор ставить нельзя. Свободные зоны обычно на правом крае рядом с коротким
левым текстом. Чтобы bbox текстового блока отражал реальную ширину строк (а не всю
колонку), задавай блокам `display:inline-block` / `width:fit-content` — тогда проверка
пересечений точна. Осторожно: если такой блок — ПРЯМОЙ потомок flex-контейнера,
`align-items:stretch` (дефолт flex) перебивает `inline-block`/`fit-content`, и box всё
равно растянется на всю ширину → проверка даст ложное пересечение. Тогда добавь блоку
`align-self:flex-start` ИЛИ оберни текст в обычный (не-flex) блок-контейнер.

## Выдача результата пользователю

Готовые файлы (PNG/PDF/PPTX/DOCX и т.п.) недостаточно просто сохранить в рабочую
директорию или упомянуть путь к ним в тексте ответа — пользователь их так не увидит.

**Каждый раз**, когда материал готов (включая повторные версии, правки и альтернативные
варианты одного и того же баннера/слайда/документа), обязательно:

1. Приложи итоговый файл(ы) через инструмент возврата файлов (`return_files` / аналог в
   текущей среде) — это отдельное действие, не заменяемое текстовым описанием
   результата. Если в рамках одной задачи созданы несколько версий (например, светлая и
   тёмная), прикладывай их все.
2. Дополнительно укажи в ответе полный путь(и) к файлу(ам) в рабочей директории
   (например, `/workspace/.../banner.png`) — чтобы пользователь мог открыть их для
   внутреннего просмотра прямо в VS Code, а не только как вложение.

## Дефолт по фону: баннеры и соцматериалы

Для отдельных визуалов (квадратные баннеры и сторис для соцсетей, обложки,
инфографика-одностраничник) **по умолчанию предлагай пользователю вариант на ЦВЕТНОМ
фоне** — тёмный холодный градиент, и показывай его первым. Светлый вариант делай, когда
пользователь его попросил (или явно захотел «оба»).

Эталон цветного (тёмного) фона:
- Фон: `linear-gradient(135deg,#32487D 0%,#337D76 100%)` (единственный крупный градиент —
  холодный; тёплый рыжий добавляется сплошной формой/glow, не вторым градиентом).
- Текст — белый; логотип — белый; рыжий `#FE6A00` обязателен как акцент (сплошная
  карточка/шеврон/форма, не текстом на синем — рыжий текст на синем рябит).
- Карточки-метрики — «liquid glass»: полупрозрачная матовая заливка, верхняя световая
  грань, мягкая тень; одна акцентная карточка — сплошная рыжая.

Если просят СВЕТЛЫЙ вариант — ориентируйся на принятый светлый рецепт:
- Фон: чистый холодный светлый градиент `linear-gradient(135deg,#FFFFFF,#EEF2F7)`.
  НЕ заливать чисто белым и НЕ уводить в тёплый/бежевый — тёплый светлый фон мутит.
- Текст: заголовок чёрный, акцент — рыжий `#FE6A00`; на цветных карточках — белый.
- Карточки: одинаковая нейтральная холодно-серая тень у всех
  `0 12px 30px rgba(50,72,125,.12)`; цветные тени не использовать (дают грязь).
- Рыжий — сплошными формами (карточка/шеврон), не мутной заливкой.

Оговорка: это правило про ОТДЕЛЬНЫЕ баннеры/соцвизуалы. Для многослайдовых презентаций
действует ритм из манифеста (светлый фон — база, зелёные/синие развороты — акценты).

## Что этот скилл не делает

Не редактирует брендбук/манифест/движок — это задача приватного авторского скилла
`brandbook-glowbyte`. Этот скилл только использует уже опубликованные данные.
